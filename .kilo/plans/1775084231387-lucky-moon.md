**Created:** 2026-04-01
**Status:** Draft

## Executive Summary

FunctionFly has a strong sandbox foundation (Wasmtime WASM, Firecracker MicroVM stubs, `SandboxClient` daemon, capability model, result caching). This plan addresses the **highest-impact gaps** across three pillars: security hardening, performance optimization, and completing the daemon migration. Work is ordered to ship the most critical improvements first.

## Phase 1 — Critical Security Hardening (Weeks 1–3)

These are **high-severity gaps** that expose the host process or allow cross-tenant data leakage.

### 1.1 Per-Execution KV Namespace Isolation

**Why:** Two concurrent functions can race on the shared in-memory KV store. Tenant A's `kv.get("config")` could return Tenant B's value.

**Where:** `runtimes/local/src/kv.rs`, `runtimes/local/src/handlers.rs`, `runtimes/local/src/host_functions/`

**Changes:**
- Prefix all KV keys with `{tenant_id}:{function_id}:` before storage/retrieval
- Pass `tenant_id` and `function_id` from Go → Rust in the execution request JSON (add fields to the request schema in `server.rs`)
- Add a `NamespacedKVStore` wrapper that auto-prefixes; keep the raw `SharedKVStore` for internal engine use only
- Update host functions in `host_functions/kv.rs` to use the namespaced wrapper

**Verification:** Write an integration test that runs two functions concurrently (different tenants) and asserts their KV spaces are isolated.

### 1.2 Wasmtime ResourceLimiter (Hard Memory Cap)

**Why:** `memory_mb` is declared in config but Wasmtime's linear memory can grow beyond it. A malicious function can OOM the host.

**Where:** `runtimes/local/src/engine.rs`, `runtimes/local/src/resource_limiter.rs`

**Changes:**
- Implement `wasmtime::ResourceLimiter` trait on a struct that checks `memory_consumed() <= max_bytes` in `memory_growing()`
- Set `Store::limiter()` during instance creation in `engine.rs:execute` (line ~179)
- Default cap: `config.memory_mb * 1024 * 1024` bytes
- Ensure the limiter also caps table elements and instances

**Verification:** Write a test function that tries to grow memory beyond its limit and verify it traps with an OOM error.

### 1.3 Wall-Clock Timeout on WASM Execution

**Why:** CPU fuel doesn't map 1:1 to wall-clock time. A function doing I/O-heavy host calls can run indefinitely while consuming minimal fuel.

**Where:** `runtimes/local/src/engine.rs:execute` (line ~179), `runtimes/local/src/config.rs`

**Changes:**
- Wrap the `spawn_blocking` call with `tokio::time::timeout(Duration::from_millis(config.timeout_ms), ...)`
- On timeout, call `engine.increment_epoch()` to trigger epoch interruption, then abort the blocking task
- Return a structured `TimeoutError` to the Go layer

**Verification:** Write a function that sleeps via a host call for 10s with a 1s timeout and verify it returns a timeout error.

### 1.4 seccomp-BPF Profile on Runtime Process

**Why:** If Wasmtime itself has a vulnerability, an attacker can escape the WASM sandbox and execute arbitrary syscalls on the host. A seccomp profile limits the blast radius.

**Where:** `runtimes/local/src/main.rs` (process startup), new file `runtimes/local/src/seccomp.rs`

**Changes:**
- Use the `libseccomp` crate (or `nix::sys::seccomp`) to apply a syscall allowlist after initialization but before serving requests
- Allowlist: `read`, `write`, `close`, `futex`, `mmap`, `munmap`, `mprotect`, `brk`, `accept4`, `epoll_*`, `timerfd_*`, `eventfd2`, `pipe2`, `dup`, `fcntl`, `sigaltstack`, `rt_sigaction`, `rt_sigprocmask`, `clone` (threads only), `exit_group`
- Deny: `execve`, `execveat`, `fork`, `clone3`, `mount`, `umount2`, `ptrace`, `bpf`, `kcmp`, `perf_event_open`, `open_by_handle_at`
- Gate behind a `--enable-seccomp` flag (default: true in production, false in dev)
- Log seccomp violations to the security monitor

**Verification:** Run the runtime with `--enable-seccomp`, attempt a blocked syscall from a test host function, verify it returns EPERM and is logged.

### 1.5 Per-Execution KV Namespace in Go Layer

**Why:** Even with Rust-side namespacing, the Go layer should pass the correct identifiers and not rely on defaults.

**Where:** `internal/api/handlers/registry/execution/sandbox.go:250-265` (args), `server.rs` request parsing

**Changes:**
- Add `--tenant-id` and `--function-id` args to the runtime process spawn in `ensureRuntimeRunning`
- Include `tenant_id` in the HTTP execution request body from `SandboxClient.Execute`
- Rust server parses these and passes them to the namespaced KV wrapper

## Phase 2 — Performance: AOT Module Cache (Week 3–4)

### 2.1 Serialize Compiled Modules to Disk

**Why:** Every cold start recompiles the WASM binary (~50–200ms). AOT serialization reduces this to ~0.1ms deserialization.

**Where:** `runtimes/local/src/engine.rs`, `runtimes/local/src/module_cache.rs`, `runtimes/local/src/config.rs`

**Changes:**
- Add `aot_cache_dir: PathBuf` to `Config` (default: `{temp_dir}/aot-cache/`)
- After `Module::new()`, call `module.serialize()` and write the bytes to `{cache_dir}/{sha256(wasm_bytes)}.cwasm`
- On cache hit, use `unsafe { Module::deserialize(engine, &bytes) }` instead of `Module::new()`
- Integrate into `ModuleCache` (the LRU at `engine.rs:33`) so it checks disk on miss
- Add `--aot-cache-dir` CLI arg and wire it through `SandboxClient` and `SandboxExecutor`

**Verification:** Cold-start timing benchmark: first request (compile + cache) vs second request (deserialize from cache). Target: <5ms deserialization.

### 2.2 Store Precompiled Modules in the Registry DB

**Why:** Avoid per-node compilation. When a function is first compiled on any node, store the `.cwasm` bytes so other nodes can deserialize immediately.

**Where:** `internal/storage/registry/function_crud.go`, `migrations/` (direct SQL), `internal/api/handlers/registry/execution/sandbox.go`

**Changes:**
- Add `wasm_compiled BYTEA` column to `registry_function_versions` table (direct SQL, not golang-migrate due to duplicate sequence numbers)
- On publish: compile WASM → serialize → store `wasm_compiled` alongside `wasm_binary`
- On execution: if `wasm_compiled` exists, send it to the runtime as base64 in the request body; runtime deserializes instead of compiling
- Invalidate `wasm_compiled` when `wasm_binary` changes (hash comparison)

**Verification:** Publish a function, verify `wasm_compiled` is populated. Execute on a fresh runtime instance, verify it deserializes without recompilation.

## Phase 3 — Daemon Migration (Week 4–5)

### 3.1 Wire SandboxClient as Default Executor

**Why:** `SandboxExecutor` spawns a new OS process per request (~200ms overhead). `SandboxClient` is implemented but not wired as the default.

**Where:** `internal/api/handlers/registry/execution/execution.go`, `internal/api/handlers/registry/execution/sandbox.go`, `cmd/orchestrator-api/`

**Changes:**
- Initialize `SandboxClient` at API server startup (in `cmd/orchestrator-api/main.go` or equivalent init)
- Pass the `SandboxClient` to execution handlers via dependency injection (add to handler struct or context)
- Replace `NewSandboxExecutor()` calls in `executeLocallyWithLimits` with `SandboxClient.Execute()`
- Keep `SandboxExecutor` as a fallback for single-function verification and testing (gate behind a `--use-legacy-executor` flag)
- Add health check / watchdog for the daemon process; auto-restart if it dies

**Verification:** Start the API, send 10 concurrent execution requests. Verify only one `functionfly-local` process exists. Measure p99 latency improvement.

### 3.2 Per-Function Resource Limits in Daemon Mode

**Why:** The daemon handles multiple functions. Each function needs its own memory/CPU/timeout limits within the shared process.

**Where:** `runtimes/local/src/server.rs`, `runtimes/local/src/engine.rs`, `runtimes/local/src/pool.rs`

**Changes:**
- Parse per-function limits from the execution request JSON (`memory_mb`, `timeout_ms`, `capabilities`)
- Apply limits per-execution via `Store::limiter()` and `tokio::time::timeout()` (from Phase 1.2 and 1.3)
- Track per-function metrics in `ResourceMonitor` to prevent noisy neighbors
- Set `max_concurrent_per_function` in the daemon's `Config`

## Phase 4 — Performance: Instance Pool & Python Runtime (Week 5–7)

### 4.1 Python Runtime Pool

**Why:** RustPython `PythonRuntime` objects are created fresh per request. WASM instances are pooled, but Python runtimes are not.

**Where:** `runtimes/local/src/python_pool.rs`, `runtimes/local/src/python/`, `runtimes/local/src/engine.rs`

**Changes:**
- Implement `PythonRuntimePool` (analogous to `InstancePool`) with LRU eviction and idle timeout
- Pool key: `{function_id}@{version}` → cached `PythonRuntime`
- On execution: check pool → warm hit? reuse runtime. Cold? create and insert.
- Apply memory pressure eviction (reuse existing `pool.rs` eviction logic)

### 4.2 Firecracker Snapshot/Restore (Enterprise)

**Why:** MicroVM cold boot is ~100–125ms. Snapshot/restore reduces this to <10ms for warm VMs.

**Where:** `runtimes/microvm/src/firecracker.rs`, `runtimes/microvm/src/orchestrator.rs`

**Changes:**
- After VM boots and initializes CPython, take a snapshot via Firecracker API (`PUT /snapshot/create`)
- Store snapshot path in `Orchestrator` warm pool
- On warm hit: `PUT /snapshot/load` instead of full boot
- Add snapshot invalidation when VM image changes

**Verification:** Benchmark: cold boot (~125ms) vs snapshot resume (<10ms).

### 4.3 COW Root Filesystem for MicroVMs

**Why:** Each VM currently gets a full copy of the root filesystem. With overlayfs, all VMs share a read-only base image and only allocate per-tenant diff.

**Where:** `runtimes/microvm/src/orchestrator.rs`, `runtimes/microvm/images/`

**Changes:**
- Create a read-only base image from `Dockerfile.python311` / `Dockerfile.python312`
- Use `overlayfs` with base=ro, upper=per-tenant tmpfs, workdir=tmpfs
- Mount the overlay as the VM's root drive via Firecracker block device config
- Reduce per-VM disk allocation from ~500MB to ~50MB (diff only)

## Phase 5 — Kernel-Level Network Isolation (Week 7–8)

### 5.1 Network Namespace per Worker

**Why:** The network whitelist is advisory — enforced at the Rust application layer, not the kernel. A compromised runtime can bypass it.

**Where:** `runtimes/local/src/main.rs`, `runtimes/local/src/config.rs`, deploy scripts

**Changes:**
- On startup, create a Linux network namespace (`unshare --net` or `netns`)
- Set up a veth pair: host ↔ namespace
- Apply `iptables`/`nftables` rules in the namespace to allow only whitelisted egress
- DNS: forward DNS queries to the host's resolver via the veth pair
- Gate behind `--enable-net-ns` flag (default: true in production)

**Verification:** Start runtime with `--enable-net-ns`, execute a function that tries to `fetch("https://evil.com")`, verify it's blocked at the kernel level.

### 5.2 YARA Scan on WASM Upload

**Why:** Malicious WASM modules could exploit Wasmtime bugs. Scanning before storage adds a defense layer.

**Where:** `internal/api/handlers/registry/`, `deploy/yara/yara_service.py`

**Changes:**
- On function publish (WASM binary upload), call the YARA service before storing in the DB
- Reject uploads that match malware patterns
- Make this async (don't block publish) with a quarantine status until scan completes
- Add `yara_scan_status` column to `registry_function_versions` (pending, clean, quarantined)

## Risks & Mitigations

| Risk | Mitigation |
|------|------------|
| AOT cache deserialization is unsafe if attacker-controlled `.cwasm` | Only deserialize bytes we compiled ourselves; store hash alongside `.cwasm` and verify before load |
| seccomp profile breaks legitimate syscalls (e.g., new Rust stdlib calls) | Start in audit/log-only mode; promote to enforcement after soak testing |
| Network namespace adds deployment complexity | Gate behind `--enable-net-ns` flag; default to false in dev, true in production |
| SandboxClient daemon becomes a single point of failure | Add watchdog that auto-restarts the daemon; fall back to per-request SandboxExecutor if daemon is unreachable |
| YARA scan adds latency to publish | Make it async with quarantine status; don't block the publish response |
